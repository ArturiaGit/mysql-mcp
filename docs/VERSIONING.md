# 版本管理规范

> 状态：拟定规则；没有应用版本、Tag、发行包或发布脚本。本次文档基线不表示已经发布 0.1.0。

## 1. 版本来源

未来应用采用 SemVer：MAJOR.MINOR.PATCH。拟以 `mysql-mcp/package.json` 为应用版本唯一来源；该文件当前不存在。管理服务、页面和 stdio 适配层首期随同一个应用版本发布，不引入多组件独立版本复杂度。

配置 schema_version、HTTP API 主版本和 MCP 协商的协议版本分别表达不同兼容边界，不直接等于应用版本。不能将 MCP SDK 版本当作客户端兼容性证据。

## 2. 递增规则

| 变化 | 拟定处理 |
|---|---|
| 兼容缺陷修复、安全修复 | PATCH，说明实际行为变化 |
| 向后兼容的新工具或能力 | MINOR |
| 删除/重命名参数、改变必填条件、破坏性配置迁移 | 稳定期 MAJOR |
| 0.x 阶段破坏性变化 | MINOR，并明确 BREAKING CHANGE 和迁移步骤 |
| 纯文档纠错、未改变软件行为 | 不要求应用升版 |

按真实兼容影响选择最小充分递增，不能用“最小版本”掩盖破坏。安全修复如果改变原契约仍需说明兼容代价。0.1.0 只能作为未来首次可运行基线的候选，不能预先标成已发布；1.0 需明确稳定契约和验收范围。

## 3. 契约与迁移

工具新增字段尽量向后兼容；输出状态扩展需考虑客户端未知状态处理。改审批规则、默认限制、凭据存储或 SQL 支持范围时，同步[接口](./API_AND_PROTOCOLS.md)、[数据模型](./DATA_MODELS.md)、[部署指南](./DEPLOYMENT_GUIDE.md)。

读取未知配置版本应拒绝写回，迁移前备份非敏感配置并说明凭据如何处理。升级不得恢复或迁移仍可执行的旧审批；旧请求失效。数据库业务数据不属于本应用配置迁移对象。

## 4. 发布流程（尚未建立）

1. 明确发布范围、兼容矩阵和未验收项，取得发布授权。
2. 运行已落地的构建/测试及相关安全检查，保留实际结果。
3. 汇总变更日志：新增、修复、安全、破坏性变化、迁移、限制。
4. 更新唯一版本来源及锁文件对应元数据，检查产物不含秘密、运行配置或业务数据。
5. 在可追溯提交上创建 `vX.Y.Z` Tag，记录产物校验值和环境。
6. 验证安装/启动与回退路径，再宣布可用范围。

以上是流程，不是当前已有命令。未来 CHANGELOG、release 脚本和 CI 单独实施，不制造不存在的链接。回退应用不能撤销已经执行的 SQL；真实补偿仍须人工二次确认。
