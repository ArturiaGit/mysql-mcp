## 1. 来源与变更规则

- S1：本地历史项目记忆，记录上一轮需求、有限环境检查及未实施状态；含本机线索，不随公开仓库上传，本文提供脱敏需求摘要。
- S2：本次对话中的用户问答：客户端、代码路径、Node.js/TypeScript、数据库权限和写入范围、确认方式。
- S3：本次只读环境检查：Windows、Node.js/npm 版本、工作区文件与 Git 状态。
- S4：本次官方公开资料调研，链接见下文；不是实机验收。
- S5：用户选择根目录 `docs/` 并批准仅文档计划。
- S6：用户批准公开仓库 ArturiaGit/mysql-mcp 及默认分支→验收→commit→push→PR 流程；PR 合并仍等待用户确认。
- S7：用户批准需求追踪、执行证据、验收与 Git 拦截门禁，允许治理脚本、Hook、CI 和 main 保护；不得以 AI 自述标完成。
- S8：用户批准 Antigravity × PI-Desktop 协作、人工转交双向 prompt 与机械责任/交接验证；本次 PI 限定引导更新规范/台账，Git 提交交由 Antigravity。
- S9：用户批准变更文档管理规约（docs/changes/ 库建设、Agent 开启新任务前强制通读未发版变更、发版说明无缝聚合与 PR/Commit 链接）。
- S10：用户明确确认当前处于本地开发环境，数据库中均为造的假数据，可以随便用；明确不需要也不能强制开发 Mock 协议桩，业务写入与 DDL 均在开发环境假数据库真实执行。

用户最新明确答复覆盖旧需求；助手提出但未获明确确认的方案仍是提案。事实不能因计划获批而变成实现事实。原记忆作为历史保留。

## 3. 需求变化与范围

S1 的“当前仅只读”被 R06、R07、R09 更新，不再是项目总范围；读取工具本身仍必须拒绝写操作。S1 建议专用只读账号是早期建议，不应与用户“按 DBA 账号权限执行受审批写入”的要求混淆。不得根据历史资料默认使用高权限账号。

首期产品范围为连接管理、元数据查询、读取、受审批业务写入和常见库表 DDL。账号/授权管理、服务器管理、通用 SQL IDE、数据库备份恢复、自动建业务库不作为首期承诺。具体 SQL 子语法覆盖由解析器验证后记录；无法安全支持的语句明确拒绝，不伪装成账号无权限。

跨库语句、过程/触发器管理、批量脚本、用户自管事务等首期排除项属于拟定实现边界，见约束文档；不是用户已逐项确认的额外需求。

## 6. 授权边界

当前批准了规范编写、公开 Git 仓库初始化及 R15 默认流程。软件实施、安装依赖、写入系统凭据、改客户端配置和真实数据库操作均不因文档或 Git 授权自动获准。即使将来批准软件开发，也不替代 R09 要求的每次数据库变更确认；但开发阶段经 S10 确认直接连接包含假数据的开发库，不需要也不开发 Mock 协议桩。初始工作区无 Git 的记录是历史事实，后续初始化见 Git 工作流。
