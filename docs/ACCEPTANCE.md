# 需求追踪、执行证据与验收门禁

> 状态：治理实现规范。应用功能尚未实现；实际门禁运行、CI 和保护状态见[验证索引](./verification/README.md)，功能逐项见[派生状态表](./FEATURE_STATUS.md)。

## 1. 为什么需要脚本

仅有 Agent 提示词、计划和 Markdown 复选框不足以阻止虚假完成。原流程没有机器追踪的功能 ID、覆盖关系、验收执行记录或远程检查。本轮将约束落实到本地 Hook、版本绑定检查及独立 GitHub Actions。语义正确性仍需真实测试和审查，不能声称脚本理解全部业务。

## 2. 单一登记与任务启动

- `governance/features.json`：稳定功能 ID/key、需求、行为、依赖、实现/测试路径、验收项和必要证据类型。复合需求拆为功能及独立验收项，不能用“数据库支持”一个项目代替所有 SQL/客户端。
- `governance/tasks.json`：任务、类型、分支、基线、功能、授权范围、允许路径、PR。修改前先登记并搜索现有实现、测试与 PR。
- `governance/checks.json`：可运行检查的命令/参数数组、超时、解析器和关联验收项。当前仅 Node 内置测试，无业务依赖安装。
- 修改已登记功能应复用 ID；修复必须说明回归标准，扩展须说明新增验收范围，不建立同义重复功能。
- 同一功能不能被冲突的活动新增任务重复占用。允许路径是授权上限，不证明该路径内任何功能都获授权。
- 需求/标准删除或降级必须显式说明范围变化，治理脚本与工作流修改需 `governance_change`。该声明仍需用户审查，不是 AI 自行扩大授权的凭证。

## 3. 实际操作

在仓库根执行（无需 npm install）：

```text
node scripts/governance/check.mjs
node scripts/governance/run.mjs
node scripts/governance/report.mjs --write
node scripts/governance/install-hooks.mjs
```

最后一个命令只在获授权的仓库安装本地 Hook；已有 hooksPath 或自定义 Hook 不自动覆盖。普通 report 默认只读；生成的 `docs/FEATURE_STATUS.md` 必须与登记一致。新文件须进入明确暂存集后再执行基于 Git 跟踪快照的检查，不以未跟踪文件充当实现证据。

提交前读取暂存快照，不使用未暂存修改掩盖错误；推送前检查 stdin 中实际 ref/OID，对待推送提交重新检查及执行必要测试。main/master 直接提交或推送、删除 ref、不匹配任务分支均拒绝。CI 根据 PR base/head 检查完整范围并独立执行。

## 4. 硬拦截

| 类别 | 拒绝条件 |
|---|---|
| 完整性 | 未覆盖确认需求；无效需求引用；功能/标准/任务 ID 或规范化 key 重复；依赖缺失/成环 |
| 任务 | 无对应活动任务、冲突新增任务、已实现功能再次 new、变更越出登记路径 |
| 范围变更 | 删除需求/功能/验收项无变更记录；改检查器/标准/工作流未声明治理变更 |
| 路径 | 越出仓库、不存在或未跟踪的实现/测试、秘密/本地记忆快照进入提交 |
| 执行 | 非零退出、超时、零测试、失败、跳过、格式异常；不能只有 passed=true |
| 证据 | 无输入/检查定义摘要、版本、时间、命令、结果和产物；输入变化后旧证据失效 |
| 完成 | 缺必要自动/实机/人工证据、依赖未完成、用模拟替代实机、手改派生状态或路线图勾选 |
| Git | main/master 操作、错误实际推送分支/对象、必要门禁失败 |

计划阶段没有实现文件不阻止登记，但不能据此变成已实现/完成；未来申请更高状态需要完整证据。

## 5. 执行记录与可信度

执行器使用可执行文件及参数数组，禁任意 shell 拼接。记录 schema、任务、功能、验收项、源提交/快照摘要、检查定义摘要、命令、环境、开始/结束、退出码、测试总数/失败/跳过，以及输出文件和摘要。报告与自身输出不纳入被测输入，避免自引用；源码、测试、配置或锁文件变化需重跑。

本地报告用于诊断，不能成为独立完成功能的证书。GitHub Actions 应在对应提交独立运行，保留 run/job/artifact 可查链接；复制 CI 字段到本地 JSON 不能产生信任。原始输出只使用合成数据，禁止真实凭据/SQL/结果入公开日志。

产物存在保留期限，过期或不可访问时必须标证据不可核查。记录失效不等于业务代码自动失效，但不能继续声称本次证据可复验。

## 6. 状态与安全默认

| 维度 | 含义 |
|---|---|
| 实现 | planned / in_progress / implemented，implemented 仍不是完成 |
| 验证 | 未执行 / 失败 / 本地验证通过 / 独立验证通过 / 证据过期 |
| 验收 | 未验收 / 未通过 / 已验收 |
| 交付 | 未提交 / PR 待合并 / 已合并 |

“完成”必须由必要标准、版本匹配的独立验证、真实人工/实机验收及交付共同推导，不提供自填 completed 入口。当前没有可信外部证据认证器时，门禁拒绝升级为已验收/完成；不会因为 JSON 字段齐全而接受 AI 写的证明。治理脚本自己也只能报告本轮测试通过，不能替用户批准自身。

人工验收需版本、环境/客户端版本、步骤、预期/实际、验收人和真实证据位置。数据库 DML/DDL 测试须隔离库、账号权限及逐次批准。当前用户与 Agent 共用 gh 账号，单凭账号评论、merge 或自称真人不能证明独立人工操作；更高保证需独立 reviewer 或可信签名流程，未落实前不伪装具备。

## 7. 远程防线与限制

本地 Hook 可被改写或 --no-verify 绕过，因此 main 配置 PR 和必需 governance 状态检查、基线同步、禁 force push/删除，并查询 API 核实。首个 PR 携带门禁自身，必须由用户审查；后续修改门禁不能靠自己的声明替代审查。

Actions 采用只读权限，不使用 pull_request_target 或把秘密注入 PR 代码。仓库所有者仍可更改保护，同权限 Agent 不可能被自己可更改的规则绝对约束。门禁降低可观测的偏离风险，不声称完全消除语义遗漏、恶意造假或管理权限绕过。

## 8. 日常交付

每次报告逐功能状态、实际命令/结果/版本、证据链接、失败或未执行及原因。CI 成功不抹掉实机/人工未执行；文档检查不当作数据库功能通过。按原 Git 约定更新 PR 后等待用户确认，不自动合并。
